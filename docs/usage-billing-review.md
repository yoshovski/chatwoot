## Behavior

- Existing subscription: current recurring price, cadence, status, renewal/end date, billing period, latest invoice and management action. No checkout selector or “Continue” button.
- No online subscription: explicit absence, a note for separately billed accounts, monthly/yearly offers and an explicit “Subscribe” action. This page does not invent a paid status for manually managed accounts.
- Ended/expired subscription: explain its state and offer a new subscription only when eligible.
- Deferred paid renewal: label the operator-granted payment extension explicitly, rather than calling it a free trial. Ended subscriptions use Stripe's actual end timestamp when available.
- Payment issue: explain the problem and emphasize invoice/payment management. Paid-client reply behavior and trial quota policy remain governed by the existing service rules.
- Payment-provider refresh failure: keep saved details visible with an explicit warning and retry. Hide new checkout until verification succeeds; checkout also checks the provider on the server.
- Change billing: active single-item, automatically charged, flat licensed monthly/yearly subscriptions can review a frequency change in Stripe. The server refreshes and verifies the account subscription, prepares account-specific catalog prices and a portal configuration, and opens `subscription_update_confirm` for the existing item. Quantity is preserved; current price is shown separately from the alternate saved offer. Stripe shows prorations/credits, collects payment and handles authentication. Creating a review session does not change or charge the subscription.
- Cancellation: show “Renewal off” and the scheduled end date. The change dialog directs the customer to resume in Stripe before returning to choose a different frequency. Never silently resume a cancellation as part of opening a frequency change.
- Portal eligibility: payment issues, trialing subscriptions, multiple items, metered prices, unsupported intervals, tiered prices, currency changes, schedules and pending updates use ordinary portal management. The server repeats eligibility checks against current Stripe state before opening confirmation.
- Responsive presentation: wrap labels/dates and use a single-column offer selector on narrow screens. Native radio controls, focus rings, semantic definition lists, an accessible chart and optional exact daily totals, and alert text provide keyboard/screen-reader support.

## Source-of-truth rules

Stripe is authoritative for the existing subscription and latest invoice. The saved account offer controls new checkout pricing. Invoice totals may differ from recurring item prices due to taxes, discounts, credits and one-time charges. Conversation allowance counts 24-hour conversation windows rather than tokens or model spend. The daily timeline uses each window’s actual start date; resetting the monthly allowance does not erase past daily usage. The display starts when account tracking was created and includes up to the last 30 UTC calendar days. Tenant cost attribution is described in [LiteLLM tenant usage](ai-agents/litellm-tenant-usage.md).

Primary references:

- [Stripe subscription lifecycle](https://docs.stripe.com/billing/subscriptions/overview): distinguish active/trial/payment-failure/end states.
- [Stripe subscription integration](https://docs.stripe.com/billing/subscriptions/build-subscriptions?payment-ui=checkout&ui=stripe-hosted): use webhooks and customer portal management for existing subscribers.
- [Stripe invoice lifecycle](https://docs.stripe.com/invoicing/integration/workflow-transitions): distinguish draft, open, paid, void and uncollectible invoices.
- [Stripe portal deep links](https://docs.stripe.com/customer-management/portal-deep-links): review an update to a specific subscription with payment/authentication handled by Stripe.
- [Stripe portal configuration](https://docs.stripe.com/customer-management/configure-portal): allow account-specific product prices and invoice prorations.
- [Stripe portal limitations](https://docs.stripe.com/customer-management): restrict self-service changes to supported subscription structures.

## Rollout and validation

Run the database migration before application/workers. Add the invoice webhook types listed in [account billing](chatoctave-account-billing.md). Existing customers are reconciled when an administrator opens Billing or attempts checkout; ordinary usage polling reads local webhook state. Review deployed Stripe portal settings and perform monthly/yearly test-mode checkout, failure recovery, cancellation and checkout return after deployment. Local fixtures do not establish that production invoices are paid or that deployed gateway tracking is complete.

Local validation: 230 existing Ruby examples, 15 subscription-component scenarios, fixture-based Stripe reconciliation/checkout checks and two-tenant chat/embedding header checks passed. Ruby lint and targeted frontend lint had no errors; the production Vite build passed. Follow-up validation: 27 existing Ruby regression examples and 18 subscription-component scenarios passed. It uses the complete settings layout and real billing/chart/dialog components with local fixtures at desktop and mobile widths. The overview cards have matching desktop heights, the body has no horizontal overflow, and scrolling ends at normal bottom padding. Daily history fixtures cover repeated reset timestamps, zero-use dates and reset preservation; Stripe SDK fixtures verify hosted annual confirmation without charges, cancellation preservation and payment-issue rejection. Live payments and Dify attribution remain rollout checks.
